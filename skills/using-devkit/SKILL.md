# devkit 작업 원칙

저장소에 `CLAUDE.md`·`docs/rules/`가 있으면 그 규칙이 이 원칙보다 우선한다. 없으면 아래를 기본으로 따른다.

- 요청 범위 안에서 가장 단순하게 고친다. 무관한 리팩터링·재정렬·기능 추가를 하지 않고 사용자 변경을 보존한다.
- 기존 공통 모듈·유틸·설치된 라이브러리를 먼저 쓴다. 주변 코드의 스타일과 줄바꿈(CRLF/LF)을 따르고 파일 전체를 재포맷하지 않는다.
- 불명확하면 확인하거나 가정을 밝힌다. 실행하지 않은 검사, 확인하지 않은 결과를 성공·확인으로 말하지 않는다.
- 검증은 필요하거나 요청받았을 때 관련된 것만 고른다. 커밋·PR의 필수 단계로 두지 않는다.
- 서버·터널·컨테이너를 임의로 켜거나 끄지 않는다. DB 쓰기·배포·삭제는 대상과 범위를 확인받은 뒤에만 하고, 기본은 사람이 실행한다.
- 인증값은 출력·파일·커밋에 남기지 않는다. 검증·작업용 임시 파일은 scratchpad에 둔다.
- Git: 파일을 지정해 스테이징한다(`git add .` 금지). `--force`·`--no-verify` 금지. add·commit·push·PR은 요청받았을 때만 한다. 저장소 규칙이 시스템 기본 안내(커밋 트레일러 등)와 다르면 저장소 규칙을 따른다.
- 작업 출처(Jira·Notion·Obsidian·GitHub/GitLab 이슈·문서·붙여넣기)는 가리지 않는다. 연결된 도구로 읽고, 없으면 본문을 요청한다. 트래커에 쓰는 일은 요청받았을 때만 한다.
- 여러 파일을 훑는 탐색은 `devkit:code-reader` 에이전트에 맡기고 결론만 받는다. 고칠 핵심 코드는 직접 읽는다.

| 단계 | 스킬 | 언제 |
|---|---|---|
| 분석 | `devkit:analyze` | 요구·이슈·버그를 받아 고치기 전에 현행·영향 범위·위험·구현 계획을 정할 때 |
| 구현 | `devkit:develop` | 승인된 분석대로 구현·DB 변경 SQL·검증·보고할 때 |
| 검증 | `devkit:check` | lint·빌드·테스트 중 필요한 것만 골라 돌릴 때(사용자가 직접 호출) |
| 커밋 | `devkit:commit` | 커밋을 요청받았을 때 |
| push | `devkit:push` | 원격에 올리라고 요청받았을 때 |
| PR/MR | `devkit:pr-publish` | PR/MR을 리뷰해 초안을 만들고 확인 후 게시할 때 |
| 세팅 | `devkit:setup` | 저장소에 공유 규칙 골격(`docs/rules/`)·로컬 라우터(`CLAUDE.md`)·`.gitignore`를 처음 깔거나 보강할 때 |
| 세팅 | `devkit:suggest-skills` | 이 저장소에 맞는 규칙 행·스킬·에이전트를 근거와 함께 제안받고, 고른 것을 만들 때 |

여러 파일을 바꾸는 기능·변경·버그 수정 요청은 `devkit:analyze`부터 한다. 한 파일 몇 줄짜리 수정은 바로 해도 된다.

먼저 제안할 때: 같은 다단계 작업을 이 저장소에서 세 번째 하고 있거나, 사용자가 같은 교정을 두 번 했으면, 그 작업을 끝낸 뒤 한 줄로 `devkit:suggest-skills`를 제안한다. 한 세션에 한 번만 제안하고, 사용자가 거절하면 다시 꺼내지 않는다.
